# Issue #218 — JWKS per-kid negative cache and coalescing tests

Follow-ups from the #208 review (Grok 4.7 at `5235756f`).

## Problem

The 60s forced-refresh throttle was **per cache**: any unknown `kid` (including garbage) blocked every other unknown `kid` for 60s. Coalescing and rate limits were easy to bypass when callers used stale wall-clock `now` values or cancelled mid-flight.

## Change

In `activity_bridge.py`:

- **Per-`kid` negative cache** (`forced_refresh_negative_kids`: LRU `OrderedDict`, max **128** entries, **60s** window).
- **Global floor**: **`JWKS_FORCED_REFRESH_GLOBAL_MIN_INTERVAL_SECONDS` (1s)** on **`time.monotonic()`**, stamped under `refresh_lock` when a forced attempt is **admitted**, before the fetch task starts (counts cancelled/failed attempts too).
- **Single in-flight refresh** (`refresh_task` + `refresh_waiter`): forced and TTL refreshes share one cache-owned `asyncio.Task`; all callers `await asyncio.shield(task)`. The task stores success/failure on the cache; its `finally` clears the waiter synchronously (no lock await before `set_result`). Results apply only when `admitted_now >= cache.fetched_at` and the generation matches.
- **`_jwks_monotonic()`** is patchable in tests.
- `validate_inbound_jwt` / `validate_inbound_jwt_bf` pass `unknown_kid=kid` into `_refresh_jwks`.

## Tests

Regression coverage for cancelled leaders/waiters, forced+TTL single fetch, per-kid 59s/60s with injected monotonic time, and existing integration/coalescing cases.

## Bounds summary

| Knob | Value |
|------|-------|
| Per-`kid` no-refetch window | 60s |
| Negative-cache LRU size | 128 `kid`s |
| Global min interval between forced attempts | 1s (monotonic) |

Tokens whose `kid` is absent from a freshly fetched JWKS are still rejected (fail closed).
