# Issue #244 — plain-flush retry nits

Follow-up to PR #243 / #238 plain-flush retry work.

## Changes

1. **`turn_buffer_flush` typing** — `_send_reply_activity` now annotates the flush guard as a 3-tuple `(chat_id, buf, segment_ids)` matching callers.

2. **Handoff link-alone post** — The separate handoff suffix plain post passes `tuple(drop_ids)` into the flush guard so `_plain_flush_retry_still_valid` re-checks informative-only segments still present after backoff, instead of treating an empty id list as always valid.

3. **Concurrent flush during plain retry** — When `_flush_closed_turns` returns early because `plain_reply_flush_in_progress`, it sets `plain_flush_followup` only if buffered segment ids are not fully covered by `plain_reply_flush_segment_ids` (segments the in-flight plain post already owns). Clearing the in-progress flag in `_send_reply_activity` schedules one deduped `_flush_turn_buffer` follow-up task.

## Tests

- `TestTurnBufferPlainFlushRetry.test_handoff_link_flush_retry_rechecks_drop_segment_ids` — real adapter flush path through `_flush_closed_turns` with handoff link-alone + HTTP 429 retry; removing drop segments during backoff must not produce a third POST.
- `TestTurnBufferPlainFlushRetry.test_plain_flush_busy_arms_followup_flush_for_later_segments` — concurrent `_flush_turn_buffer` while plain send hangs, cancel plain send, follow-up task delivers buffered text.
